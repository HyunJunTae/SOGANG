Pintos Project 1: User Program
 
담당 교수 : 박성용
이름 / 학번 : 태현준
개발 기간 : 2026.09.10 ~ 2026.09.20
개발 목표
OS의 여러 필수 기능이 누락되어 있는 Pintos 상에서 일반적인 ELF 유저 프로그램이 정상적으로 실행될 수 있도록 커널의 필수 기능들을 구현한다.
가장 먼저 사용자가 입력한 명령어 문자열을 파싱하여 유저 스택에 인자를 저장하고 커널로 전달하는 과정을 구현한다. 그 후, 유저 가상 메모리와 커널 메모리를 분리하고 포인터의 유효성을 검증하여 잘못된 접근으로부터 시스템 보호를 구현한다. 나아가 유저 프로그램이 커널의 기능을 안전하게 사용할 수 있도록 인터럽트 기반의 시스템 콜 핸들러를 구축하고, 프로세스 및 파일 시스템 제어를 위한 기본 시스템 콜과 두 가지 사용자 정의 시스템 콜(fibonacci, max_of_four_int)을 구현한다. 마지막으로 다중 프로세스 환경에서의 파일 시스템 접근 동기화 처리를 수행하고 올바른 프로세스 종료 메시지 출력 기능을 추가함으로써, 안정적인 유저 프로그램 구동 환경을 구축하는 것이 이번 과제의 세부 목표이다.
개발 범위 및 내용
개발 범위
아래 각 항목을 구현해야 하는 이유, 그리고 구현 시 기대되는 결과를 간략히 서술
Argument Passing
구현 이유 : 유저 프로그램을 실행할 때 전달하는 명령어와 옵션, 인자를 프로그램 내부로 전달하기 위해 필요하다.
기대 결과 : 커널이 전달받은 인자 문자열을 올바르게 파싱하여 유저 스택에 적재함으로써, 유저 프로그램(echo 등)이 정상적인 동작을 수행할 수 있다
User Memory Access
구현 이유 : 유저 프로그램의 버그나 악의적인 의도로 인해 커널 영역의 데이터나 코드가 손상되는 것을 방지하기 위해 필요하다.
기대 결과 : 시스템 콜 호출 시 전달된 포인터를 엄격히 검증하여, 잘못된 메모리 접근이 감지될 경우 해당 프로세스만 안전하게 강제 종료시키므로 OS 전체의 안정성이 보장된다.
File Descriptor
구현 이유 : 하나의 프로세스가 동시에 여러 개의 파일을 열고 접근할 수 있도록 각각의 열린 파일을 식별하고 관리할 수단이 필요하기 때문이다.
기대 결과 : 프로세스마다 독립적인 파일 디스크립터 테이블을 가지게 되어 체계적인 입출력 작업이 가능해지며, STDIN(0)과 STDOUT(1)을 포함한 파일 입출력을 정상적으로 처리할 수 있다.
System Calls
구현 이유 : 유저 모드에서는 메모리 할당, 프로세스 제어, 디스크 파일 접근 등 커널이 관리하는 시스템 핵심 자원에 직접 접근할 수 없으므로, 이를 대행해 줄 안전한 인터페이스가 필요하다. 
기대 결과: 프로세스 제어 및 파일 I/O와 관련된 다양한 시스템 콜이 구현되어, 일반적인 유저 어플리케이션이 Pintos 상에서 정상적으로 실행되고 종료될 수 있다.
Synchronization in Filesystem
구현 이유 : Pintos의 기본 파일 시스템은 내부적인 동기화를 지원하지 않아, 다수의 프로세스가 동시에 파일 읽기/쓰기를 시도할 경우 데이터 오염이나 커널 패닉 등 경쟁 상태 문제가 발생한다. 이를 방지하기 위해 필요하다.
기대 결과: 여러 스레드가 동시에 파일 시스템에 접근하더라도 데이터의 일관성과 무결성을 안전하게 유지할 수 있다

Argument Passing
커널 내 스택에 argument를 쌓는 과정 설명
유저 프로그램을 로드하는 과정에서 전달받은 인자 문자열을 공백을 기준으로 분리한 후, 각 인자의 실제 문자열 데이터 값들을 유저 스택의 맨 위부터 먼저 쌓는다. 그 후 메모리 접근 효율을 위한 4바이트 맞춤을 수행하고, 각 문자열의 주소를 담고 있는 배열 요소(argv)들과 argv 배열의 시작 주소, 인자의 총개수(argc), 그리고 마지막으로 가짜 반환 주소를 80x86 호출 규약에 맞춰 스택에 순차적으로 쌓아 커널에서 유저 프로그램으로 제어권을 넘긴다.
User Memory Access
Pintos 상에서의 invalid memory access 개념을 간략히 설명
Invalid memory access를 어떻게 막을 것인지 설명
Invalid memory access 개념 : 유저 프로그램이 시스템 콜 등을 호출할 때, 시스템에 치명적인 오류를 일으킬 수 있는 유효하지 않은 메모리 주소(NULL 포인터, 페이지 테이블에 매핑되지 않은 가상 메모리, 커널 주소 영역인 PHYS_BASE 이상의 메모리)를 참조하려는 시도를 뜻한다.  
방어 방법: 시스템 콜 처리 전, is_user_vaddr() 함수를 사용하여 주어진 포인터가 유저 가상 메모리 영역 내에 있는지 1차로 확인한다. 이후 pagedir_get_page()를 통해 해당 가상 주소가 실제 물리 메모리에 정상적으로 매핑되어 있는지 2차로 확인하여, 하나라도 조건을 만족하지 못하면 접근을 차단하고 해당 프로세스를 종료시킨다.

구현에 이용할 자료구조와 선택한 이유를 서술

System Calls
시스템 콜의 필요성에 대한 간략한 설명
이번 프로젝트에서 개발할 시스템 콜에 대한 간략한 설명 (하나의 시스템 콜 당 최대 3문장으로 간략히 설명; 3문장을 넘길 정도로 길게 작성하지 말 것)
유저 레벨에서 시스템 콜 API를 호출한 이후 커널을 거쳐 다시 유저 레벨로 돌아올 때까지 각 요소를 설명
시스템 콜의 필요성: 보안 및 시스템 보호를 위해 OS는 가상 메모리를 유저 영역과 커널 영역으로 분리하여 유저 프로그램의 직접적인 하드웨어 접근을 통제한다. 따라서 유저 프로그램이 파일 시스템이나 메모리 관리 등 OS의 기능이 필요할 때, 권한을 안전하게 상승시켜 작업을 요청하기 위한 시스템 콜 인터페이스가 필수적이다.  
개발할 시스템 콜 설명:
halt: 시스템 전체를 끄는 기능을 수행한다. 내부적으로 shutdown_power_off()를 호출하여 Pintos를 안전하게 종료한다.  
exit: 현재 실행 중인 유저 프로그램을 종료한다. 내부적으로 thread_exit()과 process_exit() 함수를 호출하여 프로세스 이름과 상태 코드를 출력한 뒤 상태값을 커널에 반환한다.  
exec: 지정된 실행 파일을 적재하여 자식 프로세스를 새롭게 생성한다. 내부적으로 커널의 process_execute() 함수를 호출하여 실행 흐름을 넘긴다.  
wait: 자식 프로세스가 종료될 때까지 부모 프로세스의 실행을 멈추고 대기한다. 내부적으로 thread_yield()를 사용하거나 바쁜 대기(Busy waiting) 기법을 활용해 자식의 상태 값을 확인하고 반환받는다.  
create / remove: 지정한 초기 크기로 새로운 파일을 생성하거나 기존에 생성된 파일을 삭제한다. 내부적으로 커널 파일 시스템 API인 filesys_create()와 filesys_remove()를 각각 호출하여 처리한다.  
open / close: 지정된 경로의 파일을 열어 파일 디스크립터를 반환받거나, 열려있는 특정 파일을 닫는다. 내부적으로 filesys_open()을 호출하여 파일을 열고, file_close()를 호출하여 파일을 닫는다.  
filesize: 특정 파일 디스크립터에 해당하는 열려있는 파일의 크기(Byte)를 반환한다. 내부적으로 해당 파일 객체의 file_length()를 호출하여 처리한다.  
read / write: 지정된 파일 디스크립터를 통해 버퍼로 데이터를 읽어오거나 기록한다. 내부적으로 표준 입출력(STDIN, STDOUT)은 input_getc()와 putbuf()를 호출하며, 일반 파일은 file_read()와 file_write()를 호출하여 처리한다.  
seek / tell: 열려있는 파일 내에서 읽기/쓰기를 수행할 오프셋(위치 포인터)을 이동시키거나 현재 위치를 반환한다. 내부적으로 해당 파일 객체에 대해 file_seek()와 file_tell()을 호출하여 동작한다.  
fibonacci / max_of_four_int: N번째 피보나치 수열 값을 구하거나 주어진 4개의 정수 중 가장 큰 값을 반환하는 프로젝트 추가 구현 사항이다. 별도의 기존 커널 API 호출 없이 시스템 콜 핸들러 내에 직접 연산 로직을 구현하여 처리한다.
시스템 콜 API 실행 흐름: 유저 레벨에서 시스템 콜(예: open())을 호출하면, 매크로를 통해 시스템 콜 번호와 인자들이 유저 스택에 PUSH되고 int $0x30 인터럽트가 발생하여 커널 모드로 진입한다. 이후 intr_entry에서 기존 레지스터 상태를 백업한 후 syscall_handler가 호출되어 스택 포인터(esp)를 참조해 요청된 커널 기능을 수행한다. 처리가 완료되면 리턴 값을 eax 레지스터에 저장하고, 스택을 원래 상태로 복원한 뒤 유저 모드로 다시 돌아온다.
Synchronization in Filesystem
Lock, Semaphore를 어떻게 이용할 수 있는지 각각에 대해 살명 (다른 방법을 서술해도 되지만, lock과 semaphore는 반드시 포함해야 함)
Lock 이용 방법: 파일 시스템 작업 전반을 감싸는 전역 락을 선언하고 lock_init()으로 초기화한다. 여러 스레드가 동시에 file_read나 file_write 등을 호출하는 Critical Section 직전에 lock_acquire()를 호출하여 다른 프로세스의 진입을 차단하고, 작업이 끝난 직후 lock_release()를 호출하여 락을 반환함으로써 한 번에 하나의 프로세스만 파일 시스템에 접근하도록 제어한다.  
Semaphore 이용 방법: struct semaphore를 선언하고 초기값을 1로 설정하여 Binary Semaphore 형태로 구성한다. 락과 동일하게 파일 시스템 접근 직전에 sema_down()을 호출해 세마포어 값을 0으로 줄여 타 프로세스의 접근을 막고, I/O 작업 완료 후 sema_up()을 호출해 값을 다시 1로 늘려주어 상호 배제를 달성할 수 있다.

수정하거나 추가해야 하는 자료구조

2. User Memory Access
수정해야 하는 소스코드
- userprog/syscall.c, userprog/exception.c  
수정하거나 추가해야 하는 자료구조
- 별도로 추가하는 자료구조는 없으며, 기존 프로세스의 페이지 디렉토리 테이블을 활용한다.  
수정하거나 추가해야 하는 함수
- check_address() (사용자 정의 함수 추가): 전달받은 포인터가 PHYS_BASE 아래의 유저 영역인지(is_user_vaddr()), 그리고 할당된 물리 메모리가 존재하는지(pagedir_get_page()) 검사하는 함수를 새롭게 작성한다.  
- syscall_handler(): 시스템 콜 인자로 포인터가 전달될 때마다, 위에서 만든 검사 함수를 호출하여 유효성을 판별하도록 수정한다.  
- page_fault(): 유효하지 않은 메모리 접근으로 인해 페이지 폴트가 발생했을 때, 커널 패닉을 막고 해당 프로세스만 종료(exit(-1))하도록 예외 처리 로직을 수정한다.  
3. File Descriptor
수정해야 하는 소스코드
- threads/thread.h, threads/thread.c, userprog/process.c
수정하거나 추가해야 하는 자료구조
- struct thread (수정): 스레드 제어 블록 구조체 내부에 열린 파일 객체(struct file *)들을 관리할 파일 디스크립터 테이블(정적 배열)과, 다음에 할당할 FD 번호를 기억하는 정수형 변수를 추가한다.
